# MarrowAI Security Specification

## Security objectives

Protect the Linux host from incorrect, unauthorized, destructive, or spoofed actions while preserving user control and auditability. Security decisions apply on the server/executor side, never only in the UI.

## Authentication and authorization

- The baseline identity is the local Linux account, with additional application authentication unresolved under DEC-012.
- Scoped sudoers rules and Linux capabilities are required; blanket root is prohibited.
- Every operation is checked against a server-side allowlist and validated arguments.
- Moderate/Destructive voice actions require speaker verification in addition to ordinary authorization.
- The exact roles and permissions are unresolved under DEC-013; at minimum distinguish operator, administrator/configurator, audit reader, and kill-switch authority if the deployment needs them.

## Input and output validation

- Validate request length, encoding, action schema, targets, paths, arguments, provider responses, timestamps, IDs, and confirmation fingerprints.
- Reject malformed model JSON, unknown operations, unexpected fields where strict schemas apply, and unsupported execution paths.
- Treat model output as untrusted data, not code.
- Use argument arrays/APIs instead of shell concatenation; enforce path and target policies.
- Sanitize stdout/stderr and UI rendering to prevent terminal/UI injection.
- Redact credentials, tokens, raw audio, and embeddings from logs and error messages.

## Sessions, tokens, and secrets

- Never place provider keys, sudo credentials, speaker embeddings, or signing material in source control.
- Use OS-protected secret storage or environment/service-manager secret injection selected at deployment time.
- Confirmation tokens must be short-lived, single-use, bound to action ID and plan fingerprint, and unusable after cancellation/expiry.
- Do not persist raw audio by default. Encrypt speaker embeddings at rest and support deletion/re-enrollment.
- Hosted model calls require explicit consent/data-disclosure policy and must send only approved data.

## API security

- Enforce authentication and authorization on every protected route.
- Use bounded request sizes, rate limits for planning, confirmation, speaker verification, and status endpoints, and idempotency for submissions.
- Protect against replay by action fingerprint, token expiry, lifecycle state, and idempotency key.
- Do not trust client-provided risk tier, outcome, privilege, or execution path.
- Return generic safe errors while retaining diagnostic detail in protected logs.

## Command and GUI execution security

- Maintain a reviewed operation/argument allowlist.
- Run with the least privilege needed for the selected operation.
- Avoid `shell=True` and unescaped interpolation.
- Apply timeouts, output limits, cancellation checks, and process-group cleanup.
- GUI automation must verify target identity via accessibility data or approved vision confidence rules before input simulation. Exact thresholds are [DECISION REQUIRED].
- Dry-run must be non-executing by construction and tested as such.

## eBPF and kernel security

- Load only signed/reviewed or otherwise approved eBPF artifacts according to deployment policy.
- Require verifier acceptance, capability checks, bounded maps/loops, and explicit attach-point policy.
- Never load a custom kernel module or unreviewed generated bytecode.
- Treat verifier rejection, capability denial, and kernel incompatibility as degraded/unavailable states.
- Keep complex inference in user space; do not pass arbitrary model bytes into the kernel.

## Common attack prevention

Address command injection, argument/path traversal, privilege escalation, prompt injection through retrieved text, model-output injection, replayed confirmations, spoofed voice, denial of service through oversized input/output, log injection, secret leakage, stale-state execution, and unauthorized audit access.

Retrieved examples and conversation memory are untrusted content and must not override system policy or operation allowlists.

## Audit requirements

Record request identity, validated plan version/fingerprint, risk decision and reasons, confirmation/speaker result, selected executor, privilege mode, start/end, outcome, cancellation, and governor interventions. Audit records are append-only to ordinary application roles, access controlled, sanitized, and subject to a defined retention policy. Retention is DEC-010.

## Security verification

Run dependency/license/security scanning, static analysis, secret scanning, privilege-boundary tests, malformed-model tests, command-injection tests, replay tests, authorization matrix tests, eBPF verifier/capability tests, and audit-integrity tests before release.
